# Fork 三轨操作契约

## 不变量

1. 官方提交与本地定制必须可区分。
2. 镜像分支名是 `upstream/<上游默认分支>`（上游默认分支为 `main` 时就是 `upstream/main`）。它只能快进到 `upstream` 远端的默认分支。
3. `dev` 是二开集成点。
4. `main` 是发布分支（原先叫 `release`）。它只接受已经在 `dev` 验证过的结果，不直接合并上游。
5. 自动化不能用强制重置、强推或清理命令消灭证据。

## 引用写法

本地分支 `upstream/main` 与远程跟踪引用 `refs/remotes/upstream/main` 同名，短名字会歧义。脚本和手工命令要写完整引用：

- 镜像分支：`refs/heads/upstream/<默认分支>`
- 上游尖端：`refs/remotes/upstream/<默认分支>`

## 初始化验收

- `git remote -v` 能看到 `origin` 与 `upstream`，或明确记录当前只存在官方远端、尚未建立用户 `origin`。
- `upstream/HEAD` 可解析。
- 镜像分支与 `refs/remotes/upstream/<默认分支>` 处于相同提交或可快进关系，且没有用户独有提交。
- `dev` 不承载在镜像分支上。
- `main` 若缺失，从镜像尖端创建，不从已经混入二开的提交创建。
- 若 `main` 已经含有镜像里没有的提交，停止破坏性整理并报告；那些提交可能是旧的二开，需要人工迁到 `dev`。

## 同步验收

- 同步前工作区干净。
- 已执行 `git fetch upstream --prune --tags`。
- 镜像分支使用 `git merge --ff-only refs/remotes/upstream/<默认分支>` 完成更新。
- 合入 `dev` 前存在回退分支。
- 冲突若发生，人工或工具按业务意图解决，并重新运行门禁。
- 门禁失败时没有进入 `main`。
- 默认不同步后自动把 `dev` 合入 `main`。只有显式打开提升开关，并且验证已经通过时，才提升。

## 放弃一条二开线

默认只有一条活跃二开分支 `dev`。若必须放弃当前 `dev` 又要保留它：冻结该分支，从干净镜像另开 `dev2`。不要随意再叠 `dev3`。已有仓库把活跃工作留在 `dev2` 的，视为历史债务，不作为新 Fork 的模板。

## 推荐维护节奏

高频更新仓库不要积压太久再升级。按项目活跃度建立固定同步节奏；重大安全修复出现时立即单独处理，不等常规同步周期。
